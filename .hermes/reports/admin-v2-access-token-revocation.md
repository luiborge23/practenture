# Admin V2 Access-Token Revocation Evidence

Date: 2026-07-28  
Branch: `admin-console-v2`

## Outcome

Implemented per-user JWT access-token invalidation at the password-change boundary without changing auth response models or token field names.

- Production access-token issuance now adds a precise UTC `iat` claim through `_create_access_token`.
- `_verify_token` resolves the token subject and compares `iat` with `users.password_changed_at`.
  - `iat < password_changed_at`: rejected.
  - `iat == password_changed_at`: accepted.
  - Legacy token with no `iat` and a populated `password_changed_at`: rejected.
  - Legacy token with no `iat` and no boundary: retains legacy behavior.
- Password reset updates `password_hash` and `password_changed_at`, consumes the reset token, revokes refresh tokens, and revokes owner admin sessions in one SQLite transaction.
- The direct authenticated password-change path advances `password_changed_at`; transparent hash migration/bootstrap paths do not.
- Owner, professor, student, Apple/Google, registration/activation, refresh, professor invitation, and SAML access-token issuance retain their existing claims and response contracts while gaining `iat`.

## Regression Coverage

Added `backend/tests/admin_v2/test_password_reset_access_token_revocation.py` covering:

1. Owner and professor access tokens work before reset and fail after successful reset.
2. Existing refresh-token revocation remains effective.
3. Existing owner admin-session revocation remains effective.
4. A new login/access token after reset is valid.
5. Failed reset attempts do not set `password_changed_at` or invalidate the access token.
6. Timestamp comparison is deterministic at the equality boundary.
7. Legacy no-`iat` compatibility follows the required boundary rules.
