# Admin V2 SQLite Transaction Isolation Evidence

**Date:** 2026-07-28
**Scope:** P1-1 shared-connection transaction ownership only
**Branch:** `admin-console-v2`

## Baseline

The rereview demonstrated that `AdminSessionRepository._transaction()` used the legacy process-wide `sqlite3.Connection(check_same_thread=False)`. An unlocked legacy `Database.update_user_password()` call could therefore commit an Admin V2 transaction owned by another thread.

## Implemented repair

- Give `Database` a non-invasive factory for consistently configured connections bound to the instance's actual database path.
- Give every Admin V2 transaction a dedicated connection, explicit `BEGIN IMMEDIATE`, commit/rollback, and close.
- Give Admin V2 read-only helpers their own short-lived connection.
- Add deterministic mixed-thread regression coverage using real SQLite and the real legacy writer.

The mixed-thread test synchronizes a dedicated Admin transaction and the real unlocked legacy password writer with a barrier. A trace event proves the legacy `UPDATE` starts while Admin holds the `BEGIN IMMEDIATE` write lock. The Admin mutation is then forcibly rolled back; the legacy writer finishes afterward. A fresh observer connection confirms the Admin row is absent and the unrelated password update is durable.
